# 추론 파이프라인 정리 (`dacon_final_pipeline.ipynb`)

나라장터 입찰공고 1건마다 고정 모델 **Gemma 4 26B**(`google/gemma-4-26B-A4B-it`)가 24개 위반 항목의 0/1과 근거 문구를 판정하는 파이프라인입니다.
학습·LoRA는 없고, **RAG(유사 사례 검색)와 프롬프트·규칙**으로 성능을 올립니다.

---

## 1. 전체 흐름

```
공식 데이터 + unlabeled.csv
  │ ① 사례은행 만들기: 법령 발췌 + 자동 라벨 사례 + 사람 라벨 사례 (+ Gemma pseudo)
  ▼
공고 1건
  │ ② 구조 기반 청킹 → 의심 항목 9개 선정 → 하이브리드 검색(dense + BM25)
  │ ③ 프롬프트: 항목 기준 + meta + 법령 발췌 + 대조 사례 + 공고 발췌
  ▼
Gemma (vLLM, JSON 구조화 출력, temperature 0)
  │ ④ 후처리: 근거 문구 원문 검증, 적용 불가 항목 0 처리
  ▼
submission.csv (49열)
```

단계별로 dev Macro F1을 재서 **점수가 오르는 경우에만** 다음 사례를 채택합니다.

| 단계 | 사례은행 | 역할 |
|---|---|---|
| LAW-ONLY | 법령·규칙만 | 기준점 |
| AUTO-WEAK | + `unlabeled.csv` 자동 라벨 사례 991개 | 자동 라벨 효과 확인 |
| AUTO+HUMAN | + 사람 라벨 사례 447개 | 사람 라벨 효과 확인 |
| +PSEUDO | + Gemma 자가 라벨 고확신 양성 | 낮아지면 자동으로 버림 |
| 제출 자산 | 위에서 고른 자산 + dev 정답 사례 | dev 정답은 **단계 선택이 끝난 뒤에만** 추가(점수 누수 방지) |

## 2. 적용한 방법론

### 2-1. RAG 검색

| 방법 | 내용 | 근거(측정값) |
|---|---|---|
| **항목 라우팅 확대** | 사례를 붙이는 항목 4개 → 9개, 법령 발췌 항목 수(6)와 분리 | dev 정답 위반 중 사례를 받는 비율 40.5% → 59.5% |
| **하이브리드 검색** | BGE-M3 dense + 문자 bigram BM25, 가중 RRF(k=60) 결합 | BGE learned sparse를 섞으면 검색 AUC가 낮아져(0.51) 빼고 BM25로 대체(0.556) |
| **대조 사례(contrastive few-shot)** | 항목마다 위반 사례 1 + 비슷하지만 위반 아닌 사례 1을 나란히 제시, 같은 공고 중복 금지 | 판정이 갈리는 조건을 비교하게 함 |
| **Contextual Retrieval** (Anthropic) | 사례·질의 조각 앞에 "어느 계약·어느 조항인지" 문맥 줄(CTX)을 붙여 검색. 선택 시 Gemma가 문맥을 생성해 자산에 저장 | 규칙 문맥만으로 BM25 AUC 0.552 → 0.562 |
| **구조 기반 청킹** (kt cloud 청킹 전략) | 공고문을 조항 제목(3. / 가. / ①) 단위로 자르고 상위 조항 제목을 붙임, 긴 조항은 15% 겹침 | 정답 근거 문구가 공고 발췌에 들어가는 비율: 3500자 0.60 → 0.71, 1700자 0.29 → 0.49 |
| **근거 중심 사례 창** | 사례 본문을 근거 문구 앞 150자·뒤 450자로 잘라 420자로 표시 | 이전에는 프롬프트에서 잘릴 때 근거가 빠지는 문제 |

시도했지만 뺀 것: BGE learned sparse, meta 유사도 채널, ColBERT 재순위화(메모리), 질의에 항목 정의 붙이기, 검색 기반 항목 라우팅, LLM 재순위화.

> 검색만으로 위반/비위반을 가르는 힘(AUC)은 방법과 상관없이 0.5~0.6 수준입니다. 이 과제는 금액·계약방법 같은 세부 조건으로 판정이 갈리기 때문에, 검색의 역할은 "정답 맞히기"가 아니라 **비슷한 조항과 판정 기준을 Gemma에게 보여주는 것**입니다.

### 2-2. 프롬프트·출력

- 시스템 프롬프트에 24개 항목의 판정 기준(dev 기준으로 맞춘 규칙, `데이터 라벨링.md` 2-2)과 "사례는 참고일 뿐 법령보다 우선하지 않음"을 명시
- 사용자 프롬프트: 나라장터 meta 21개 필드 + 규칙 점수 힌트 + 법령 발췌 + 대조 사례 + 공고 발췌
- 출력은 JSON 스키마로 강제(`v` 24개, `e` 24개)
- 16K 토큰을 넘으면 공고 발췌·법령·사례 양을 단계적으로 줄임(11단계)

### 2-3. 후처리·안정성

| 처리 | 내용 |
|---|---|
| 근거 검증 | 원문 부분문자열이 아니거나 500자 초과·`=+@` 시작이면 근거만 비움(판정은 유지) |
| 적용 불가 항목 | 협상계약이 아니면 v22·v23 = 0, 국가계약이면 v23 = 0 등 |
| 출력 실패 | 한 번 실패하면 더 긴 출력으로 재시도, 두 번 실패하면 그 공고만 전부 0(전체 실행은 계속) |
| 중단 대비 | `--resume`: 공고마다 체크포인트(`*.partial.jsonl`)에 저장, 다시 실행하면 이어서 진행 |
| 메모리 부족 | vLLM 로드 실패 시 컨텍스트를 16384 → 12288 → 8192로 자동 축소 |

## 3. 반영된 데이터

| 데이터 | 반영 방식 |
|---|---|
| `unlabeled.csv` 자동 라벨 19,600행 | 항목당 양성 최대 40 + hard negative 4 → weak 사례 991개 |
| `unlabeled.csv` 사람 라벨 400행 | 양성 전부 + 항목당 hard negative 8 → 사례 447개, 검증셋(기본 150건) |
| dev 200건 정답 | 평가에만 사용, 제출 자산에는 단계 선택 후 few-shot으로 추가 |
| 법령 패키지 | 항목별 고정 법령 발췌(국가/지방 구분) |
| 중기부 경쟁제품 목록 | 경쟁제품 판정(v10·v11·v13) |

## 4. 실행 환경

노트북은 GPU VRAM을 보고 프로필을 자동으로 고릅니다.

| | 제출물 기본값(평가 서버) | `a100` 프로필 (Colab A100, VRAM ≥ 38GB) | `rtx3090` 프로필 (24GB) |
|---|---|---|---|
| 모델 | 원본 `gemma-4-26B-A4B-it` | 원본(대회 고정 revision) | `cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit` |
| 양자화 | `int8_per_channel_weight_only` | 동일 | `awq_marlin` (4bit) |
| 컨텍스트 | 16384 | 16384 | 12288 |
| 동시 시퀀스 | 4 | 4 (80GB면 8) | 2 |
| 검색 모델 | BAAI/bge-m3 (서버 제공) | 동일 | 동일 |

- `a100` 프로필은 평가 서버와 모델·양자화·컨텍스트가 같아 dev 점수를 제출 성능의 추정치로 볼 수 있습니다. `rtx3090`은 단계 간 상대 비교용입니다.
- Colab: 입력 파일 업로드 창(`open.zip`, `unlabeled.csv`, `human_labels.csv`), HF 토큰은 보안 비밀 `HF_TOKEN`, 결과·체크포인트는 Google Drive에 저장, 런타임이 끊기면 `RESUME_WORK`로 이어서 실행
